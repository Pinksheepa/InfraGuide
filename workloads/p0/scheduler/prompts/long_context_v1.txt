请阅读以下一份虚构的推理服务运行记录，并在回答中只用三条项目符号概括：观察到的现象、不能从记录推出的结论、下一步应收集的证据。

记录背景：服务只使用一张 GPU、一个固定模型和一个 OpenAI 兼容的流式接口。记录中的时间均来自客户端单调时钟；它们不是服务端调度器的内部时间。请求内容、模型版本、采样参数和缓存状态在这份记录之外另有固定配置，但本段文本不提供这些配置值。

第 1 轮：一个较长的用户输入在零时刻被提交。客户端记录了请求开始、首个非空内容片段和流结束的时刻。该记录说明客户端看到了流式响应，但没有直接报告排队、KV 分配、token budget 或每个 scheduler step 的状态。

第 2 轮：在第 1 轮尚未结束前，短请求按照预定到达偏移被工作负载程序处理。若线程池已经满载，工作负载程序会等待空闲槽位；等待时间应被标为客户端调度延迟。这个延迟可能来自本地并发上限，不能被改写成 engine queue time。

第 3 轮：每个请求使用一个稳定 request ID。原始 JSONL 为每个 ID 保留类别、计划到达、实际 client 提交、SSE 终态、输出文本重编码 token 数和失败信息。成功记录有可能包含 DONE 与 stop，失败记录也必须保留而不是从汇总中删除。

第 4 轮：输入 token 数由固定本地 tokenizer 对同一 messages 和 chat template 参数重新计算。这个计数用于冻结工作负载长度。它仍是客户端复算值；若服务端采用的模板或版本不同，二者可能不完全相同，因此需要把来源和 tokenizer 配置保存下来。

第 5 轮：吞吐窗口从第一条实际 client 提交开始，到所有请求形成 success、HTTP failure 或 timeout 的终态结束。成功请求数除以该窗口得到 successful request/s；成功请求的本地重编码 output token 总和除以该窗口得到 output token/s。失败数量另外报告，不通过丢弃失败来改善数字。

第 6 轮：TTFT 使用请求提交至首个非空 content 的客户端时间差。TPOT 是首个至最后非空 content 的时间跨度除以本地重编码输出 token 数减一。SSE chunk 不保证一一对应生成 token，因此 TPOT 只是 estimate，不能写成服务端逐 token ITL。

第 7 轮：若一个短请求的实际提交时间位于长请求的实际提交与终态之间，可以证明两个客户端请求在飞行时间重叠。这不足以证明短请求已经被服务端 admission，也不足以证明它等待在某个具体 scheduler queue 中。

第 8 轮：若短请求没有在长请求终态前实际提交，工作负载只说明计划到达顺序，并没有制造客户端重叠。此时应调整 prompt 长度、到达偏移或有限并发配置，然后重新校准；不能把未重叠的运行解释为长短竞争。

第 9 轮：同一 trace 可以多次重放，但每次 run 都有独立 run ID、启动命令、engine 配置和原始输出路径。比较不同策略前，这些条件必须保持一致。只替换 workload 内容、模型 revision 或缓存状态会破坏比较基线。

第 10 轮：本 smoke 的目标只是验证 trace、客户端调度、时间记录和结果落盘。它不修改 vLLM Scheduler，不构成 adaptive prefill 的设计，也不构成任何延迟、吞吐或优化收益的结论。

第 11 轮：如果长输入很短，单卡小模型可能在短请求到达前就完成 prefill；如果输入过长，可能超过 engine 的上下文或显存配置。实际 token 计数和一次真实运行决定后续候选长度，不能从文字字符数直接假定 token 数。

第 12 轮：若未来需要解释短请求尾延迟，至少还需要固定版本的 scheduler 源码、服务端可验证的排队或 step 观测、KV 容量状态以及实际到达重叠。没有这些证据时，正确结论只能是客户端观测到某种时间差，原因待验证。

第 13 轮：线程池的 max_in_flight 限制的是客户端同时执行同步 HTTP 调用的数量。它不是 vLLM 的 max_num_seqs，不是 GPU batch size，也不是 scheduler token budget。所有这些参数必须在结果的启动配置中分别记录。

第 14 轮：每个 prompt 文件保存为 UTF-8 文本，并由 trace 记录 SHA-256。运行前若文本被改动，runner 应在任何请求发出前拒绝执行。这样可避免同一 request ID 悄然对应不同内容。

第 15 轮：同样地，trace 保存预期 prompt token 数。runner 以本地 tokenizer 重新计算后必须一致才发送请求。这个检查保护的是本地可重放配置，并不把本地 token 数冒充成服务端 usage。

第 16 轮：本记录是为工作负载 fixture 编写的静态测试文本。它由 AI 辅助生成后冻结为文件；runner 不会在运行期间调用任何模型来生成、改写或扩充它。文本语义不用于评价模型回答质量。
